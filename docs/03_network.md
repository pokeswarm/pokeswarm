# 03. 協力プレイ・アカウント・フレンド

印（【決定】【初期案】【要決定】）の意味は `01_game_design.md` の冒頭を参照。

## 1. アカウント

### 1.1 ログイン方式
- 【決定】Google ログインを基本とする。
- 【決定】ゲストでも遊べる。ゲストには Firebase の**匿名ログイン**で仮のアカウントを作り、Google ログイン時にそのアカウントへ Google を紐づけてデータを引き継ぐ。
- 【初期案】すでに Google でアカウントを持つ人がゲストで遊んだ後に紐づけようとした場合は、データが2つになる。どちらのデータを残すかを本人に選んでもらう。
  - 不具合（作者の指摘 2026年10月23日。直した）: 2回目以降の Google ログイン（すでにある Google のアカウントへ切り替える）で、使わなくなったゲストのアカウントを切り替えた**後**に消していた。Firebase のアカウントの削除は、消したあとに今ログインしている人をログアウトさせるので、Google のログインまで消えていた。そのため Firestore に書けずセーブが巻き戻り、ブラウザを閉じて開くとゲストに戻っていた。ゲストは切り替える**前**に消すようにした（`src/firebase/account.ts`）。この不具合の間に遊んだ分（Firestore に書けなかった分）は戻せない。
- 【初期案】フレンド機能・協力プレイは Google ログイン済みのプレイヤーのみ使える（ゲストのデータが消えて関係が失われるのを防ぐため）。
- 【決定】Google のメールアドレスは他のプレイヤーに一切表示しない。
- 【決定】（2026年10月22日、作者の判断）引き継ぎコード: ゲストだけが使える。タイトルのログインの窓の「引き継ぎコード」から、元のブラウザで発行し、新しいブラウザで入力して受け取る。**有効期限は24時間**（`data/game/save.json` の `transferHours`）、**1回きり**（受け取ったら消す）、**移した後も元のブラウザのデータはそのまま**（写し）。受け取る前に、受け取るデータと今のデータを並べて、置き換えてよいか確かめる。
  - 実装: コードは見間違えやすい文字（0・O・1・I）を除いた32文字から12文字（60ビット。暗号用の乱数。`src/meta/transferCode.ts`）。Firestore の `transfers/{コード}` に `from`（発行した人）・`data`（セーブデータの写し）・`expireAt` を置く。コードを知っている人だけが1件ずつ読め（一覧は読めない）、期限を過ぎたら読めない。受け取りはトランザクションで読み直してから消す（`src/firebase/account.ts`）。同じブラウザで発行し直すと、前のコードは消す。個人情報は入れない。
  - 期限切れで残ったものは、Firestore の TTL（`transfers` の `expireAt`）で自動で消す（作者が Firebase の画面で設定する）。
- 【決定】（2026年10月22日、作者の判断。A 案）Google の許可画面には「名前・メールアドレス・プロフィール写真を共有」と必ず出る（Firebase の Google ログインの決まりで外せない）。メールアドレスを渡したくない人のために、(1)「Google でログイン」を押したら、先に説明の窓を出す（ゲームでは使わず保存も表示もしない・ほかのプレイヤーに見えない・ログインの記録として管理者だけが見られる Firebase に残る・ゲストのまま遊べる）。(2) メールアドレスなしでデータを移せる「引き継ぎコード」を用意する。ゲームのコードは名前・写真・メールアドレスを読まない。
- ログインはポップアップ方式を基本とする（ブラウザのサードパーティ Cookie 制限でリダイレクト方式が失敗する場合があるため）。
- Firebase の承認済みドメインに、`localhost`・開発用アドレス・`pokeswarm.org` を登録する。

### 1.2 表示名
- 初回ログイン時に表示名を決めてもらう。フレンドに表示される名前。
- 【決定】（2026年10月21日、作者の判断）Google でログインした後にニックネームを登録すると、**「ニックネーム#1234」**の形のタグ（Discord の旧方式と同じ）が付く。数字4桁は自動で割り当てる。重複を防ぐのは「ニックネーム＋4桁」の組み合わせなので、1つのニックネームにつき9999人まで使え（ニックネームが違えば同じ4桁でよい）、人数の上限にはならない。友達追加・招待ではニックネームと4桁の両方を正しく入力して、唯一の1人を指す。このタグで友達追加・招待をする（2章のフレンドコードの代わり）。
- 【初期案】タグの重複は Firestore の「タグ → ユーザー」の文書をトランザクションで作って防ぐ。ニックネームの大文字・小文字・全角半角は区別しない形で照合する。ニックネームを変えるとタグも新しくなる（古いタグは使えなくなる。フレンドの関係はユーザー ID で持つので切れない）。
- 【決定】（2026年10月21日、作者の判断）ニックネームは1〜12文字。空白だけ・改行・見えない文字は不可。禁止語の一覧は最初は持たない（フレンドにしか表示されないため）。いつでも変えられる。

## 2. フレンドと招待

- 【決定】フレンドリストからの招待で合流する。
- 「ニックネーム#1234」のタグ（1.2）を入力して申請し、相手が承認するとフレンドになる。
- オンライン状態は Realtime Database の切断検知（`onDisconnect`）で表示する。
- 招待は Firestore または Realtime Database に招待の記録を書き込み、相手の画面がそれを受け取って通知を出す。
- 【決定】途中参加は認めない。ラン開始後はルームに入れない。
- 【初期案】最大人数は4人。

## 3. 協力プレイの通信

### 3.1 構成
- **ホスト主導**: ルームを作った人がホストになり、敵の出現・HPの集計・撃破の確定・ボスの行動・レベルアップの候補作成を担う。
- **接続**: ブラウザ同士を WebRTC（DataChannel）で直接つなぐ。接続の仲介（シグナリング）は Firebase で行う。
- **つながらない場合**: 【決定】Firebase Realtime Database 経由の中継に切り替える。中継時は送信頻度を下げるなど、通信量を抑える。

### 3.2 同期の方式
敵が数百体いるため、全敵の位置を毎回送る方式は使わない。

| 対象 | 方式 |
|---|---|
| 雑魚敵の移動 | 各ブラウザで計算する。雑魚は「一番近いプレイヤーへ向かう」だけなので、出現情報とプレイヤーの位置があれば同じ動きを再現できる |
| 雑魚敵の出現 | ホストが「いつ・どこに・何を」を送る（シード付き乱数で補完） |
| 雑魚敵のずれ | ホストがときどき位置を補正する |
| 撃破 | ホストが確定し、「誰がとどめを刺したか」を付けて全員に送る |
| 中ボス・ボス・伝説 | 数が少ないため、位置・HP・技の発動をホストがすべて送る |
| プレイヤー | 各自が自分の位置・入力を送る |
| 経験値・レベル | ホストが管理し、全員に送る |
| 経験値の玉・拾える物 | 玉はホストが撃破を確定したときに、倒した位置に作る（玉の番号は敵の番号から決まり、全員で同じ）。吸い寄せの動きは各ブラウザで計算。拾ったかは触れたプレイヤーのブラウザが判定してホストへ伝え、ホストが先着で確定して全員へ送る |
| ノックバック | 攻撃したプレイヤーのブラウザが、命中と一緒に押し返す向きと強さをホストへ送る。自分の画面ではすぐに押し返して見せる。ホストは自分の敵に適用して全員へ送る |
| 状態異常 | 付いたかどうか（確率の判定）は攻撃したプレイヤーのブラウザで決め、命中と一緒にホストへ送る。ホストが確定して全員へ送る（遅くなる・止まるなど、敵の動きに関わるため全員でそろえる）。継続ダメージの集計はホスト |
| プレイヤーの HP | 各自が自分の HP を管理し（敵に触れた・ボスの技が当たったかは自分のブラウザで判定）、全員へ送る |
| ポーズ | ホストだけがポーズでき、全員へ送る（`01_game_design.md` 9章） |

### 3.3 当たり判定
- 【決定】自分の攻撃が敵に当たったかは**各自のブラウザ**で判定し、ホストに伝える。ホストは HP を集計し、撃破を確定する。
- ランキングがないため、改ざんの影響は本人のアンロックが進むだけで、他人には及ばない。

- 【決定】自分が敵に触れた・ボスの技が当たったかも**自分のブラウザ**で判定する（`01_game_design.md` 2.3）。見えたとおりに当たる・避けられる。

### 3.4 敵の管理
- 【決定】プレイヤーは自由に動ける（同じ画面にいる必要はない）。
- 敵の出現と移し替えは、各プレイヤーの周囲で行う。
- 敵の数は「全体の上限」と「プレイヤー1人あたりの上限」で管理し、人数が増えてもホストの負荷が一定以上にならないようにする。
- 離れたプレイヤーの周囲の敵の情報は送らない（自分の周囲の分だけ受け取る）。

### 3.5 レベルアップ時
- レベルアップでホストが全員のゲームを止め、全員分の候補をまとめて作って配る。
- 持ち物の重複を防ぐ決まり（「誰かがすでに持っている持ち物は候補に出さない」「同じ回で同じ持ち物を複数人に出さない」）は、2026年10月21日に作者の決定で廃止。
- 全員が選び終えるか、約15秒たったら再開。時間切れは「見送る」と同じ扱い。
- 【決定】（作者 2026年10月25日）自分が選び終えた後は、画面を少しだけ暗くして「ほかのプレイヤーの選択を待っています……」と出す。全員が選び終えたら、ほんの少しだけ間を取ってから再開する（【初期案】0.6秒。`leveling.json` の `coopResumeDelaySeconds`。その間は「まもなく再開します」）。時間切れのときはすぐ再開。
- 再開時に全員へごく短い無敵時間を付ける。

### 3.6 実績のカウント
- ホストが撃破を確定するとき、とどめを刺したプレイヤーと、その戦闘の参加者を付けて送る。
- 各ブラウザが受け取った情報のうち自分の分を数え、自分のセーブデータに記録する。
- 雑魚以外（中ボス・ボス・伝説）の撃破は参加者全員にカウントする。

### 3.7 切断
- 【決定】ホストの切断・接続不良が起きたら、ランを終了する。
- 【決定】そのランで得たコイン・実績の進み具合は、切断時点までの分を各自に保存する（ブラウザに一時保存した進み具合を使う）。
- ホスト以外のプレイヤーが切断した場合の扱い: 【初期案】そのプレイヤーだけ離脱し、ランは続ける。

## 4. 性能の前提

- ホストの端末が敵の計算を担うため、PC を前提とする（スマホ対応は将来）。

## 5. 実装メモ（2人の協力プレイの技術検証。2026年10月）

### 5.1 入り口（技術検証用）
- `?host` で部屋を作り、表示された参加用 URL（`?join=<部屋ID>`）を別のウィンドウで開く。
- `?host&relay` は直接接続を試さずに中継で始める。`?host&p2pfail` は直接接続をわざと失敗させ、時間切れで中継に切り替わることを確かめる。
- ログインは Firebase の匿名ログイン（本番のログインは `12` 章の後に作った。`02` 12章）。Firebase の設定値は `.env.local`（`.env.example` を参照）。設定値が無ければ協力プレイは使えない表示になり、ソロは動く。
- Firebase の SDK は協力プレイのときだけ読み込む（別ファイルに分かれ、ソロでは読み込まない）。

### 5.2 接続（`src/net/room.ts`）
- Realtime Database の `rooms/<部屋ID>` に、ホスト・ゲストの ID、シード、接続方式（`mode`）、WebRTC の接続情報と経路の候補を置く。ホストが切断すると部屋ごと消える（`onDisconnect`）。ゲストの ID も切断で消え、相手の切断の検知に使う。
- ルールは `database.rules.json`（技術検証用: ログインした人が `rooms/` の下だけを読み書きできる）。
- 直接接続は STUN（Google の公開サーバー）だけを使う。`data/game/network.json` の `p2pTimeoutMs`（10秒）以内に DataChannel が開かなければ、ホストが `mode` を `relay` にし、両者が中継に切り替える。TURN サーバーは使っていない（費用がかかるため。中継は Realtime Database で代わりにする）。
- DataChannel は、順番どおりに確実に届く `game` と、落ちてもよいもの（位置・補正）の `fast` の2本（6.4。前は1本だけ）。

### 5.3 同期（`src/net/sync.ts`。Phaser にも通信手段にも依存しない）
- 1回の更新で送るものを配列にまとめ、JSON の文字列1つで送る（`src/net/protocol.ts`）。出現・撃破などは数値を平らに並べて通信量を抑える。
- 届いたメッセージは入力コマンドに直し、次の更新でシミュレーションに渡す（ソロと同じ「コマンドで進む」形）。
- プレイヤー: 各自が自分の位置・向き・入力を送る。相手のプレイヤーは届いた位置をそのまま使う。
- 雑魚敵の出現・強化: ホストだけが決めて送る。ゲストは自分では出さない。
- 雑魚敵の移動: 各ブラウザで計算する。離れすぎた敵の移し替え先は共有の乱数ではなく「敵の id と移し替えた回数」から決める（乱数の使い方がホストとゲストで違っても同じ場所になる）。
- 敵の位置のずれ: ホストが一定間隔（直接接続で1秒、中継で5秒）で全敵の位置を送って補正する。
- 命中・撃破: 自分の攻撃の命中は各自のブラウザで判定する。ゲストは命中（敵・ダメージ）をホストへ送り、ホストが HP を集計して撃破を確定し、とどめを刺したプレイヤーを付けて全員へ送る。相手の攻撃は見た目だけ描く。
- ゲストは「ホストで倒されたが撃破の知らせがまだ届いていない敵」を持つため、敵の入れ物の大きさを上限の2倍にしている（あふれて出現を取りこぼす不具合があった）。
- 中継時は送る頻度を下げ（位置は3回に1回）、100ms ごとにまとめて1回書き込む。位置と補正は最新のものだけ残す。 受け取った側は、読んだ書き込みをすぐ消す（消さないと、ランの間ずっと受け取った分がブラウザの Firebase の中に残ってメモリを使い続け、データベースの量も増え続ける。07 の108章）。
- 直接接続でも、3 回の更新ぶん（毎秒 10 回）をまとめて送り、敵の位置の補正は 1 秒ごと（`network.json` の `p2p.batchTicks: 3`・`correctionIntervalTicks: 30`）。iPhone のブラウザ（WebRTC）は、受け取った回数・量に応じてメモリを使い続け、数分〜十数分でページごと落ちたため（07 の119章・120章）。
- 中ボス・ボスの HP と位置は、補正とは別の間隔で送る（`bossIntervalTicks`。直接接続は 3 回の更新ごと＝毎秒 10 回、中継は 6 回ごと）。補正の 1/3 の間隔に結び付けていたため、補正を毎秒1回にしたらボスも毎秒3回になり、ゲストでボスの突進が飛んで見えた（07 の138章）。ボスは数体なので、送る量はほとんど増えない。

### 5.4 タブが裏に回ったとき
- 裏のタブではブラウザが描画のタイミングを止めるため、そのままではシミュレーションも止まる。ホストが止まると全員が止まるので、協力プレイ中は「描画が `stalledFrameMs`（250ms）来なければタイマーで進める」ようにした。
- 裏のタブではタイマーも1秒に1回程度まで間引かれるため、1回の呼び出しで最大 `hiddenMaxTicksPerCall`（60回）まとめて追いつく。シミュレーションは進むが、送信も1秒ごとにまとまるので、相手から見た動きはカクつく。
- 「隠れているか（`document.hidden`）」ではなく「描画が止まっているか」で判断する。隠れていると判定されないまま描画だけ止まる環境があったため。

### 5.5 計測（2026年10月、同じ PC の2つのタブ、敵300〜500体）
| 方式 | 往復時間 | ホストの送信量 | 備考 |
|---|---|---|---|
| 直接（WebRTC） | 6〜30ms | 約5〜6KB/秒 | 大半は敵の位置の補正（1秒ごと） |
| 中継（Realtime Database） | 約1.2〜1.5秒 | 約2KB/秒 | 片方のタブが裏にあり、送信が1秒ごとにまとまった状態での値 |

- 中継の通信量: 2人で約2KB/秒 ≒ 1時間あたり約7MB（相手側の受信も同じくらい）。Realtime Database の無料枠（ダウンロード 1日360MB）に対して、2人・30分のランなら1回あたり数MB。4人の場合は人数に応じて増える。
- 中継の往復時間は、両方のタブが表示されている状態ではもっと短くなる見込み（未計測）。

### 5.6 まだ確かめていないこと・課題
- 別々のネットワーク（別の家・モバイル回線）の間での直接接続。同じ PC では必ず直接つながるため、中継への切り替えは `?host&p2pfail` で確かめた。
- 公開版（Cloudflare）での協力プレイ。ビルド時に Firebase の設定値（環境変数）を渡すことと、Firebase の承認済みドメインへの公開アドレスの追加が必要。
- ゲストの攻撃の命中から撃破の確定までに往復の時間がかかる（中継では1秒以上）。倒したはずの敵がしばらく残って見える。協力プレイの本実装で、ゲスト側で先に消して見せる等を検討する。
- 部屋のデータ（中継のメッセージ）はホストが抜けるまで消えない。長いランでは溜まるため、本実装では古いものを消す。

### 5.7 ノックバック・状態異常の同期（追加の技術検証2）
- 命中で付く効果（ノックバック・状態異常）は、**当てたプレイヤーのブラウザ**で決めて（状態異常が付くかの確率も）、その場で自分の画面の敵に付ける。
- ゲスト → ホスト: 命中のメッセージ（`d`）に効果を一緒に載せる（1件 8つの数値: 敵・ダメージ・攻撃したプレイヤー・ノックバックの x・y・更新回数・状態異常の番号・更新回数）。ホストは HP を減らし、効果を付ける。
- ホスト → ゲスト: 効果のメッセージ（`fx`、1件 7つの数値）で、ホストが付けた効果と、ゲストから届いた効果を全員へ送る。付けた本人は付け済みなので無視する（4人のときに、ほかのゲストへ届けるため）。
- 継続ダメージ（やけど・どく）の HP の計算と、それによる撃破の確定はホストだけが行う。ゲストは状態異常の時間だけ数え、色などの見た目に使う。撃破はこれまでどおりホストから届く。
- 遅くなる・止まる効果は、ゲストの画面でもすぐ反映される（敵の動きを各ブラウザで計算しているため）。ずれはホストの位置の補正で直る。テストでは、ノックバック・やけどを必ず付ける設定でも、補正後のずれは 80 未満だった。
- 通信量: 2人・直接接続で、ホストの送信は約 5.8KB/秒（効果が無いときとほぼ同じ。大半は位置の補正）。

### 5.8 経験値の玉の同期（追加の技術検証3）
- 玉を作るのはホストだけ。撃破を確定したときに、倒した位置に作り、玉の番号（ホストが決める）・位置・経験値を送る（`g`）。玉が上限（`data/game/pickups.json` の `maxGems`）に達していたら、新しい玉は作らず一番古い玉に経験値をまとめ、まとめた後の値を送る（`gm`）。
- 吸い寄せの動きは各ブラウザで計算する（取得範囲はプレイヤーのステータス `pickupRange`）。一度吸い寄せられ始めた玉は、範囲の外に出ても追いかける。
- 拾ったかは**触れたプレイヤーのブラウザ**で判定する。ホストはその場で確定し、ゲストは自分の画面で玉を消して見せてから「触れた」をホストへ送る（`pr`）。
- ホストは先着で確定する。玉がまだあれば経験値を足して「誰が拾ったか・経験値」を全員へ送る（`gc`）。もう無ければ（先に誰かが拾った）何もしない。経験値は `gc` で届いた分だけ足すので、同じ玉を2回数えない。テストで「2人が同じ玉に同時に触れる」場合を確かめた。
- ゲストの玉の入れ物は、確定待ちの玉の分だけ余裕を持たせる（上限の2倍）。敵と同じ理由（5.3）。
- 確認（2人・直接接続）: ホストとゲストで、撃破数・経験値の合計・玉の数がそろった（ホスト 撃破89・経験値69・玉19、ゲスト 撃破89・経験値70・玉19。1の差は見た時点のずれ）。

### 6.1 最大4人のルームと同期（区切り1）
- つなぎ方はホストを中心にした形（ホスト ↔ 各ゲスト。WebRTC か中継）。ゲストどうしは直接つながず、ゲストの状態（位置・HP）はホストがほかのゲストへ中継する（なりすましを防ぐため、送り手の分だけ）。
- 部屋（`src/net/room.ts`）: Realtime Database の `rooms/<部屋ID>` に `members/<番号>`（ポケモンの選択）・`started`（開始時の参加者）・`peers/<ゲストの番号>`（接続情報）・`relay/<ゲストの番号>`（中継）を置く。ゲストはトランザクションで空いている一番小さい番号（2〜4）をもらう。開始後は入れない（途中参加なし）。ホストが抜けると部屋ごと消える。部屋には `version`（ホストのゲームの版）を置き、ゲストは自分の版と違えば入れない（ページを読み直すよう知らせる。2026年10月31日。07 の143章）。
- 待合室（`src/scenes/LobbyScene.ts`）: タイトルで C（または `?host`）で部屋を作り、参加用 URL（`?join=<部屋ID>`）を送る。各自がポケモンを選び、全員が選んで接続が終わるとホストが開始できる。画面は、上に4つの枠（ホスト・ゲスト・ゲスト・ゲスト）を並べて各自が選んだポケモンのアイコンを出し、真ん中にソロと同じポケモンの一覧を出す（作者の案 2026年10月22日）。一覧で選ぶとすぐ自分の枠に出る（クリック・矢印キー。Enter はホストの開始）。待合室の間に届いた通信は取っておき、ランの画面に渡す。マルチはタイトル → マップの選択 → 待合室の順で、ホストが選んだ地方を部屋の `region` に書き、ゲストはそれを読んで同じ地方のプレイアブルを並べる。待合室のタイトルに地方の名前を出す。
- 同期の追加（`src/net/sync.ts`）:
  - プレイヤーの状態に HP・最大HP・倒れているかを足した（各自が自分の分を送る）。
  - レベルアップ: ホストが全員分の候補を作り（同じ回で同じ持ち物を2人に出さない）、選択の状態（候補・選び終えた人・リロール権）を変わったときだけ送る。ゲストの「選ぶ・見送る・リロール」はホストへの要望として送り、ホストが確定した強化を全員へ送って、全員のブラウザで同じ強化を当てはめる（技・持ち物・進化が自然にそろう）。全員が選ぶか15秒で再開。
  - ボスの範囲技の予告・中ボス/ボスの HP・ランの終わり・プレイヤーが抜けたことは、ホストが送る。
  - 敵の位置の補正と一緒にホストの更新回数を送り、ゲストの経過時間をそろえる（タブが裏にあって遅れた場合など）。
- 全員が倒れたら失敗（ホストが判定する）。協力プレイでは自動で復活しない（触れて復活は区切り2）。
- ゲストが抜けたら、そのプレイヤーを外してランを続ける。ホストが抜けたらゲストに知らせる（ランの終了と保存は区切り2）。

### 6.1.1 ゲストのワープ（作者の指摘。2026年10月21日）
- ゲストの画面で、敵も味方もワープすることがあった。原因: (1) 相手のプレイヤーの位置は、届いた位置をそのまま使っていた（通信の都合で位置がまとまって届くと跳ぶ）。(2) 敵の位置の補正（直接接続で1秒ごと、中継で5秒ごと）で、ずれを一度に直していた。
- 対応（`network.json` の `smoothing`）:
  - 相手のプレイヤー: 届いた位置から、押している方向へ最大 `predictTicks`（8）回分進んだと予測した位置を目標にし、毎回 `playerBlend`（35%）ずつ寄せる。
  - 敵の位置の補正: ずれを敵の入れ物（`corrX`・`corrY`）に入れ、敵の移動のたびに `enemyBlend`（15%）ずつ寄せる。
  - ずれが `snapDistance`（240）を超えたとき（移し替え・復活など）だけ一度に合わせる。
- テスト（`src/sim/netSmoothing.test.ts`）: 位置が 6 回に1回しか届かなくても、1回の更新で本人の速さの2倍より大きく跳ばない。
- まだ確かめていないこと: 別々のネットワークでの見え方（作者の次の協力プレイで確かめる）。

### 6.2 触れて復活と切断（区切り2）
- 触れて復活（`src/sim/systems/health.ts` の `touchRevive`）: 倒れた味方の `touchRange`（40）以内に、倒れていない誰かが `touchSeconds`（2秒）いると、共有の復活可能数を1つ使って復活する（HP 50%・無敵2秒。`data/game/stats.json`）。離れると数え直し。復活可能数が無ければ数えない。
  - 位置は全員のブラウザで分かるので、触れている時間は各自が数えて表示する（倒れた味方の周りの緑の円）。復活させるかはホストが決め、全員へ知らせる（`rv`）。復活した本人のブラウザが自分の HP と無敵時間を戻す。残りの復活可能数も一緒に送ってそろえる。
  - ホストは、復活させた直後の1秒は本人から遅れて届く「倒れている」を無視する（すぐ倒れ直したことにして、復活可能数を2回使わないため）。

### 6.3 ニックネーム#タグとフレンド（区切り3）
- 決まり（`src/meta/nickname.ts`）: ニックネームは1〜12文字（絵文字も1文字）。空白だけ・改行・見えない文字は不可。タグと紛らわしい「#」と、保存の都合で「/」も不可。4桁は 0001〜9999。照合は NFKC で正規化して小文字にする（全角半角・大文字小文字を区別しない）。入力の「＃」「全角の数字」も受け付ける。
- 保存（`src/firebase/social.ts`）:
  - Firestore: `profiles/{uid}`（ニックネームと4桁）、`tags/{照合用のニックネーム#4桁}`（→ ユーザー。重複を防ぐ）、`users/{uid}/requests/{送った人}`（申請）、`users/{uid}/friends/{フレンド}`（両方に置く）。
  - Realtime Database: `presence/{uid}`（オンライン状態: タイトルなど・部屋にいる・プレイ中。切断で消える）、`invites/{招待された人}/{招待した人}`（部屋の番号。招待した人が切断・部屋を出ると消える）。
- ニックネームの登録はトランザクションで、使われていない4桁を選ぶ（最大20回試す）。大文字・小文字の違いだけの変更なら4桁はそのまま。名前を変えると古いタグは消える（フレンドの関係はユーザー ID で持つので切れない）。
- 申請: 相手の「ニックネーム#1234」でタグを引き、相手の `requests` に自分の名前で書く。相手からも申請が来ていれば、そのままフレンドになる。承認すると両方の `friends` に書き、申請を消す（相手側の `friends` には、相手からの申請があるときだけ書ける。ルールで確かめる）。削除はどちらからでも両方を消す。
- 招待: 待合室のホストに、オンラインのフレンドの「招待」ボタンを出す。招待された人の画面の右上に知らせが出て、「参加する」でその部屋の待合室へ移る（ラン中は参加できない）。
- ルール（`firestore.rules`・`database.rules.json`）: フレンドの機能は Google を紐づけたアカウントだけ（`request.auth.token.firebase.identities` に google.com がある）。ゲストから紐づけた直後は、ログインの情報を取り直してから使う。メールアドレスはどこにも置かない。
- 画面: タイトルで F（フレンド画面: 自分のタグ・ニックネームの登録と変更・申請・届いた申請・フレンドの一覧とオンライン状態・削除）。タイトルのログインの表示にも自分のタグを出す。
- 確認: 決まりはテスト（6件）。2026年10月21日、作者が公開版で Google の2つのアカウントを使い、ログイン・フレンド登録・オンライン状態・招待・同時プレイ・ゲームの進行に問題がないことを確かめた。

### 6.4 遅延を減らす（作者の依頼 2026年10月25日: ホストの負荷が増えてもよいので、マルチプレイの遅延を減らしたい）
- 【決定】次の3つを入れた（TURN サーバーは後で相談）。
- **チャンネルを2本に分けた**（`src/net/peerTransport.ts`・`room.ts`）: 出来事（出現・撃破・命中・レベルアップなど）は今までどおり順番どおりに確実に届くチャンネル `game`、落ちても次が来ればよいもの（自分の位置 `p`・敵の位置の補正 `c`・往復時間の計測）は、順番を待たず送り直さないチャンネル `fast`（`ordered: false, maxRetransmits: 0`）で送る。1本だと、1つのパケットが落ちたときに後ろのメッセージが全部待たされる（回線が不安定なときの遅れの山）。`fast` が開くまでは `game` で送る。中継（Realtime Database）は今までどおり。
  - 順番を待たないので、古い位置・補正が後から届くことがある。位置には送り手の通し番号 `k` を付け（ゲストの更新回数はホストに合わせて戻ることがあるので、更新回数とは別に数える）、補正はホストの更新回数で、古いものは捨てる（`src/net/sync.ts`）。
- **敵の位置の補正を、直接接続で 1 秒ごと → 1 秒に 3 回**にした（`network.json` の `p2p.correctionIntervalTicks` 30 → 10）。ずれが小さいうちに直る。ホストの送る量は、敵の数によって 1 人あたり 1 秒に約 15KB 前後に増える（前は約 5KB）。ボスの HP も補正の 3 倍の頻度で送るので、同じく速くなる。
- **ゲストが倒した敵を先に消して見せる**（`network.json` の `smoothing.predictKillSeconds`、`src/sim/entities/enemies.ts` の `ghostTicks`）: ゲストは自分の攻撃で雑魚の HP を自分の画面でも減らし、0 以下になったら、ホストの撃破の知らせを待たずにすぐ見えなくする（描かない・当たらない・狙わない）。入れ物には残しておき、撃破の知らせ（`killEnemy`）でふつうに倒れる（撃破の数え方・経験値の玉は今までどおりホストが決める）。1.5 秒のうちに知らせが来なければ（見込みが外れた）、元の HP で見せ直す。中ボス・ボス・伝説は、HP がホストから届くので見込まない。
  - ゲストが出現させる雑魚の HP を、ホストと同じく人数で増やすようにした（前は増やしていなかった。見込みがホストとそろうように）。
- 確認: テスト（`src/sim/predictKill.test.ts`・`src/net/sync.test.ts` の古いメッセージを捨てるテスト）。同じ PC の2つのタブで、ホストとゲストの両方で `game`・`fast` の2本が開き、メッセージが種類ごとに分かれて両向きに届くことを確かめた。アプリの中のブラウザでは裏のタブが止まるため、2つのタブでランを通しで遊ぶ確認はできていない（別々の PC での協力プレイで確かめる）。
- （2026年10月25日。07 45章）待合室にゲストの「準備OK」を足した（`members/<番号>/ready`。ホストの開始の条件に入る）。
