# 06. ロードマップと版の番号

## 1. 版の番号（作者の決定 2026年10月30日）

`0.<地方>.<追加>.<修正>` の4つの数字。`data/site.json` の `appVersion` に書き、タイトル画面のロゴの右下に `BETA v…` と出す。

| 数字 | 上げるとき | 例 |
|---|---|---|
| 2つ目（地方） | 地方を公開したとき | カントー 0.1.0.0、ジョウト 0.2.0.0、ホウエン 0.3.0.0 |
| 3つ目（追加） | その地方の中の大きめの追加（新しい仕組み・技のリワーク・まとまった調整） | ジョウト公開後の協力プレイとバランスの直し → 0.2.1.0 |
| 4つ目（修正） | 小さな修正・調整 | 0.2.1.1、0.2.1.2 … |

- **公開（main への merge）ごとに上げる**（作者の決定 2026年10月31日。それまではコミットごとに上げていて、3日で 0.5.1〜0.5.56 になった）。1つの版に複数の決定が入ってよい。仕様を変えた記録は `07_content_draft.md` に章として足し、章の題には、その決定が入る公開の版（次に出す版）を書く。
- **ブランチの流れ**（同日）: ふだんのコミットは `dev`。作者が localhost で動作確認した区切り（目安は1日1回か、`07` の章がいくつか溜まったとき）で、版を上げてから main へ merge して push する。Cloudflare は main だけを公開する。merge の前に `npm run typecheck`・`npm test`（GitHub Actions `.github/workflows/check.yml` でも main・dev への push ごとに回る）。未公開の地方（ホウエンの H5 以降）も `dev` に置き、公開する版で main へ入れる。
- npm は4つの数字の版を受け付けないので、`package.json` の `version` は先頭の3つ（例: `0.2.1`）に合わせる。
- 2026年10月30日に付け直した。それまでは `0.<フェーズ>.<修正>`（カントー 0.4.x、ジョウト公開で 0.5.0、0.5.56 まで）。古い章の「版 0.4.55」などはそのまま残している。
- 【要決定】1.0.0.0 にする条件（例: 公開準備が全部終わり、作者が「ベータを外してよい」と判断したとき）。

## 2. 進め方

- 地方ごとに作る。順番は、作者に確かめること（相棒・伝説・解放の条件・難しさ）→ 区間と雑魚 → データの土台 → ショップ・実績 → プレイアブル → ボスと特別な戦い → 仕上げ（難しさの測り方・公開）。手順の細かいチェックリストは `09_knowhow.md` 1章。
- 区切りごとに、作者が動作確認できる状態にして報告する。
- 【要決定】に当たったら、仮実装で先に進めず作者に確認する。
