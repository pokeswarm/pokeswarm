# 02. 技術構成

## 1. 技術スタック

| 用途 | 採用 | 理由 |
|---|---|---|
| 言語 | TypeScript | 型でデータ構造（技・ポケモン・アンロック条件）を守る |
| ビルド | Vite | 静的サイトとして出力でき、Cloudflare にそのまま置ける |
| 描画・演出 | Phaser（実装開始時点の最新安定版） | パーティクル・トゥイーン・光や画面揺れの演出が標準でそろい、技エフェクトを作りやすい |
| 認証・保存・接続仲介 | Firebase（Authentication / Cloud Firestore / Realtime Database） | `03_network.md` 参照 |
| 協力プレイの通信 | WebRTC（DataChannel）。つながらない場合は Firebase Realtime Database で中継 | `03_network.md` 参照 |
| 配信 | Cloudflare Workers の静的アセット配信（GitHub 連携で自動公開。設定は `wrangler.jsonc`） | `05_operations.md` 参照 |

## 2. 設計の原則

1. **ゲームの状態（シミュレーション）と描画を分ける**
   - シミュレーションは Phaser に依存しない純粋な TypeScript で書く。
   - Phaser は「シミュレーションの状態を画面に描く」「入力を受け取る」だけを担当する。
   - これにより、ホストでの計算・各ブラウザでの再計算・テストが同じコードでできる。
2. **入力とゲームの状態を分ける**
   - プレイヤーの操作は「入力コマンド」として扱い、シミュレーションはコマンドを受け取って進む。
   - ソロでも最初からこの形で作る。後から協力プレイを足しても作り直しにならないようにするため。
3. **データ駆動**
   - ポケモン・技・持ち物・ステージ・敵の出現・アンロック条件・エフェクトは、すべてデータファイルで定義する。
   - コードに数値やポケモン固有の処理を直接書かない。固有技など特殊な挙動も、なるべく「効果の部品」の組み合わせで表現する。
   - 将来キャラクターを差し替えられるよう、ゲームの仕組みとポケモンのデータ・素材を分離する。
4. **固定間隔の更新**
   - シミュレーションは固定の時間刻み（初期案: 1秒30回）で進め、描画は補間して滑らかに見せる。
5. **乱数はシード付き**
   - 敵の出現などはシード付きの乱数で決め、ホストと各ブラウザで同じ結果を再現できるようにする。

## 3. 大量の敵の処理

- 敵の当たり判定・移動には **Phaser の物理演算を使わない**。自前の仕組みで管理する。
- 敵のデータは、オブジェクトの配列ではなく、項目ごとの配列（位置・HP・種類などを型付き配列で持つ形）で管理する。
- 当たり判定は**空間ハッシュ（画面を格子に区切って近いものだけを判定）**で行う。
- 敵同士の押し合い（重なり防止）は簡易的なものにとどめる。負荷の主な原因になるため。
- 描画用のスプライトは使い回す（プール）。画面外の敵は描画しない。
- 目標性能（技術検証で確認）: PC のブラウザで敵300体以上を60fpsで動かす。

## 4. 技エフェクト

- 画像素材は使わず、**パーティクル・図形・動き（トゥイーン）・光の効果の組み合わせ**で作る。
- エフェクトは「レシピ」としてデータで定義する（例: 発射体の形・色・軌跡のパーティクル・命中時の破裂）。画面を揺らす演出は使わない（具合が悪くなる人がいたため。作者の決定 2026年10月21日）。
- タイプごとに基本のレシピ（ほのお: 火の粉と赤橙の光、みず: しぶきと青い波紋、でんき: 稲妻の線と黄色のフラッシュ など）を用意し、技ごとに色や大きさを変えて量産する。
- 派生技・固有技は、基本のレシピに要素を足して見た目でも強化が分かるようにする。
- エフェクトは見た目だけを担当し、当たり判定はシミュレーション側で行う。

## 5. ドット絵の表示

- SpriteCollab のドット絵を使う。動作ごと（待機・歩き・攻撃・被ダメージなど）、8方向のスプライトシートと `AnimData.xml` の情報を、データ生成の段階で扱いやすい形に変換する（`04_data_pipeline.md`）。
- 拡大時にぼやけないよう、ドット絵向けの拡大方式（ニアレストネイバー）で描画する。
- 大きさはデータで指定する（ボスは大きく、など）。

## 6. マップ

- 繰り返して並べても継ぎ目が見えないタイル画像（128×128、1ドット＝画面2px でポケモンのドット絵にそろえる）を生成して使う。
- 時間帯（Wave）ごとに使うタイルは `data/render/ground.json` で指定する（`startSeconds` は `spawn.json` の waves と同じ値。書かなかった時間帯は前のタイルが続く）。切り替えは `fadeSeconds` かけて重ねて変える。描画は `src/render/GroundTiles.ts`。
- 元画像（`assets/map/<地方>/`）からゲーム用タイルへの変換は `node scripts/process-map-tiles.ts`（縮小・32色に減色・`preview/` に3×3の継ぎ目確認画像）。
- 同じ模様の繰り返しが目立たないよう、草・石・花などの小物を別画像で用意し、ランダムに散らす。
- マップは無限に広がる（プレイヤーの周囲だけ描画する）。

## 7. 多言語対応

- ポケモン名・技名・持ち物名は、PokeAPI から各言語の公式名を取得して使う。
- メニュー・説明文などゲーム独自の文章は、言語ごとの翻訳ファイルに分ける。コードに文章を直接書かない。
- 最初の公開版は日本語と英語。ほかの言語は後から追加できる構造にする。

## 8. セーブデータ

- ログイン中は Cloud Firestore に保存する。ゲストも Firebase の匿名ログインで同じ仕組みを使う（`03_network.md`）。
- 保存するもの: 解放済みポケモン、撃破数などの実績の進み具合、コイン、永続強化、図鑑、設定。
- 保存のタイミング: ラン終了時と、ラン中の数分ごと。Firestore の無料枠（書き込み1日2万回）に収まるよう、まとめて保存する。
- ラン中の進み具合はブラウザにも一時保存し、切断時にも失われないようにする。

## 10. 実装メモ（フェーズ0で決めたこと・分かったこと）

### 10.1 採用したバージョン・道具（2026年10月時点）
| 用途 | 採用 |
|---|---|
| 描画 | Phaser 4.2.1（`pixelArt: true` でニアレストネイバー拡大） |
| 言語 | TypeScript 7.0（型チェックのみ。変換は Vite が行う） |
| ビルド | Vite 8 |
| データの型（スキーマ）検証 | zod 4。`src/data/schema.ts` に定義し、起動時に `src/data/index.ts` で検証する |
| テスト | Vitest（`src/sim` の単体テスト。`src/sim` が Phaser・描画側を import していないこともテストで確認する） |

### 10.2 入力コマンドと固定間隔の更新
- 入力コマンドは「押している移動キーの状態」を表す（`move`: 各軸 -1/0/1 の整数）。状態が変わったときだけ発行し、次に変わるまで有効。協力プレイではこれをそのまま送る。
- シミュレーションは `Simulation.step(commands)` で1回ずつ進む。経過時間の管理は `FixedStepClock`（`src/sim/fixedStep.ts`）が行い、1フレームで追いつく回数に上限（`data/game/simulation.json` の `maxTicksPerFrame`）を設ける。上限を超えて遅れた分は捨てる（タブを裏にした後の暴走を防ぐため）。
- 描画は各エンティティの「前回の位置」と「今回の位置」を補間率で補間する。
- ブラウザ間で結果をそろえるため、シミュレーションでは環境によって結果が変わりうる `Math` の関数（`sin`・`hypot` など）を避け、四則演算・`sqrt`・定数を使う。乱数は整数演算のみの sfc32（`src/sim/rng.ts`）。

### 10.3 大量の敵（フェーズ0 区切り2）
- 敵は `EnemyStore`（`src/sim/entities/enemies.ts`）で項目ごとの `Float64Array` などに持ち、生きている敵を先頭に詰める（倒れたら末尾と入れ替え）。並び順が変わるため、通信では `id` で指す。発射体も同じ形（`ProjectileStore`）。
- 位置などを `Float32Array` にしないのは、JavaScript の通常の数値（64bit）と同じ計算結果にそろえ、再現性の確認をしやすくするため。
- 空間ハッシュ（`src/sim/spatial/spatialHash.ts`）は、格子のマスを固定長のハッシュ表に畳み込み、連結リストで要素を持つ。毎回の更新で作り直す。更新中にメモリを確保しない。
- 1回の更新の順番: 入力の適用 → プレイヤーの移動 → 出現 → 敵の移動（離れすぎたら移し替え）→ 空間ハッシュ作り直し → 敵同士の押し合い → 自動攻撃 → 発射体の移動と命中 → 倒れた敵の除去。
- 撃破は `world.events` に「どの敵を・誰が倒したか」として残す（協力プレイの同期・実績の判定で使う）。
- 出現位置などの向きは、`Math.sin`/`cos` を使わず、棄却法と `sqrt` で作る（`src/sim/math.ts`）。
- 描画は円の画像を使い回し（`src/render/PooledCircles.ts`）、画面外は描かない。
- 計測用に、URL のパラメータで上限と出現数を一時的に上書きできる（例: `?cap=3000&spawn=600`）。

計測結果（2026年10月、作者の PC・内蔵ブラウザ。表示のリフレッシュレートが約165Hz のため FPS の上限も約165）:

| 敵の数 | FPS | シミュレーション1回の処理時間 |
|---|---|---|
| 約400 | 約165 | 0.09 ms |
| 1000 | 約159〜164 | 0.14〜0.66 ms |
| 3000 | 約159 | 2.7 ms（敵が密集した状態） |

`npm run bench`（Node.js でシミュレーションだけを計測）: 300体 0.03ms、1000体 0.12ms、2000体 0.35ms、4000体 1.1ms。
1秒30回の更新では1回あたり約33msが使えるので、シミュレーションの負荷は問題にならない。描画も3000体まで60fpsを大きく上回る。

### 10.4 スプライトと技エフェクト（フェーズ0 区切り3）
- スプライトの取得・変換は `04_data_pipeline.md` 7章。ゲームは起動時に `public/sprites/<key>/anims.json` を読み、あれば Phaser のアトラスとして読み込んで、動作 × 8方向のアニメーションを登録する（`src/render/sprites/`）。向きはシミュレーションのプレイヤーの向き（各軸 -1/0/1）から決める。向きだけが変わったときはコマの位置を引き継ぐ。
- 表示の大きさ・使う動作は `data/render/sprites.json`。
- 技エフェクトのレシピは `data/effects/recipes.json`。`extends` で別のレシピを元にし、書いた項目だけを上書きできる（タイプの基本レシピ → 技ごとのレシピ）。組み立てた後に型で検証する（`src/data/effects.ts`）。
- レシピの項目: 発射体の本体（芯と光の2枚重ね・明滅）、軌跡のパーティクル、命中時の破裂・光（画面の揺れは 2026年10月21日に廃止）。パーティクルの素材は実行時に作る、ぼかした円1種類だけで、色・大きさ・寿命・重力・合成方法で見た目を変える。
- 例として、ほのおタイプの基本レシピ `fire.base` と、それを元にした `ember`（ひのこ）を作った。仮の自動攻撃は `data/game/attack.json` の `effect` でレシピを指定する。
- シミュレーションは命中を `projectileHit` の出来事として出し、描画はそれを見て命中の演出を出す。演出の揺らぎには `Math.random` を使う（見た目だけで、同期に関係しないため）。

### 10.5 貫通可能数
- 仮の自動攻撃（`data/game/attack.json`）に `pierce`（数値、または `"infinite"`）を持たせた。シミュレーションの中では無限を `Infinity` で持つ。
- 1つの発射体は同じ敵に1回だけ当たる。当てた敵の `id` を発射体ごとに `hitMemory` 個まで輪状に記録し、超えたら古いものから忘れる（その敵には再び当たりうる）。
- 同じ更新で複数の敵に重なったら、`id` の小さい順に、貫通可能数の分だけ当たる（ハッシュの並び順に左右されず、各ブラウザで同じ結果になる）。
- 体力が 0 以下になった敵（同じ更新で倒れた敵）には当たらず、貫通可能数も減らさない。

### 10.6 協力プレイ（フェーズ0 区切り4）
- 詳細は `03_network.md` 5章。シミュレーションには役割（`solo`・`host`・`guest`）と、このブラウザで操作するプレイヤーを渡す。役割による違いは「ゲストは敵を出さない」「ゲストの自分の攻撃は HP を減らさず命中を出来事として出す」「相手の攻撃は見た目だけ」の3点だけで、残りは同じコードで動く。
- 通信で届いたもの（相手の位置・出現・撃破・補正・命中）もすべて入力コマンドとして渡す。
- `src/net/` の構成: `protocol.ts`（メッセージの形）、`sync.ts`（シミュレーションとメッセージの変換）、`transport.ts`（通信路の共通の形）、`peerTransport.ts`（WebRTC）、`relayTransport.ts`（Realtime Database の中継）、`room.ts`（部屋と接続の仲介）。Firebase の初期化は `src/firebase/`。

### 10.7 敵をスプライトで描いたときの性能（追加の技術検証1）
- 雑魚敵をポケモンのスプライト（コラッタ・ポッポ・キャタピーなど10種類、歩きのアニメーション・8方向）で描くようにした（`src/render/sprites/EnemySprites.ts`）。敵の id ごとにスプライトを割り当て、画面外・倒れた敵の分はプールへ戻して使い回す。向きは移動の向きから決める。
- 敵の種類（`data/game/enemies.json`）に `sprite` を書く。全種類のスプライトがそろっていなければ、これまでどおり円で描く（公開版など）。
- 左上に「1フレームの処理」（更新の始まりから描画の命令を出し終えるまでの時間）を出すようにした。

計測結果（作者の PC・内蔵ブラウザ。FPS の上限は約165）:

| 敵の数 | FPS | 1フレームの処理 | シミュレーション1回 |
|---|---|---|---|
| 400 | 約165 | 0.38 ms | 0.22 ms |
| 1000 | 約163 | 0.79 ms | 0.88 ms → 改善後は大幅に減少 |
| 3000 | 約163 | 1.42 ms | 0.18 ms（改善後） |

- **分かったこと1（修正済み）**: 敵が1か所に密集すると、押し合いの近傍検索が周りの敵を全部集めてしまい、3000体でシミュレーションが1回7.4msまで重くなった。集める数を小さい作業用の配列の大きさまでに制限し、0.18msになった（`npm run bench` でも4000体で1.18ms → 0.29ms）。
- **分かったこと2（要対応）**: 1種類のアトラスに待機・歩き・攻撃・被ダメージ・倒れの5動作を入れると、GPU のメモリを1種類あたり約5MB使う（11種類で約55MB）。雑魚敵が使うのは歩きだけで、歩きだけなら11種類で約2.4MB。カントーの雑魚（60〜70種類）を全動作で読むと約300MBになり、性能の低い PC やスマホでは問題になりうる。**雑魚用には歩き（と必要なら被ダメージ）だけのアトラスを作り、複数の種類を1枚にまとめる**ようにデータ生成を変える。
- **分かったこと3**: 雑魚10種類のうち9種類に「倒れ」の動作が無かった（代わりに被ダメージを使う）。倒れた演出は、動作ではなくエフェクト（点滅して消えるなど）で作るほうがよい。
- **分かったこと4（見た目）**: プレイヤーが止まっていると、敵がプレイヤーの上に塊になって重なる。押し合いが弱いため。上の改善で押し合いの負荷が小さくなったので、遊びの調整（フェーズ1）で押し合いを強めてよい。

### 10.8 雑魚のスプライトの軽量化
- データ生成で、雑魚用には歩きだけの画像を作る（`data/sprites/pokemon.json` の `uses: ["enemy"]` → `public/sprites/enemy/<key>/`）。1種類あたり GPU 約5MB → 0.09〜0.47MB。10種類で約50MB → 約2.3MB。
- 出現する種類を時間帯で切り替える（`data/game/spawn.json` の `waves`）。シミュレーションはその時間帯の種類から選んで出す。
- `SpriteStreamer`（`src/render/sprites/SpriteStreamer.ts`）が、今の時間帯・次の時間帯（始まる `enemyPreloadSeconds` 秒前から）・まだ生きている敵の種類のスプライトだけを読み込み、それ以外は GPU のメモリから解放する。読み込み前の種類は仮の円で描く。
- 前の時間帯の種類の敵は、離れすぎたら移し替えずに消す（`retireOldWaveKinds`）。これが無いと前の種類が残り続け、スプライトを解放できない。消すのはホスト（ソロ）が決め、協力プレイではゲストへ知らせる（撃破には数えない）。
- 上限に達したときの強化（赤い敵）はやめた（`01_game_design.md` 2.1）。代わりに時間帯ごとの HP の倍率（`waves[].hpMultiplier`）を出現時に掛ける。
- 確認（技術検証用の仮の時間帯: 0秒〜コラッタ・ポッポ・キャタピー、40秒〜ビードルなど4種類、80秒〜ズバット・イシツブテ・パラス）: 読み込んでいる種類は 3 → 7（次の時間帯を先に読み込み）→ 3 と移り、GPU のメモリは最大でも約1.6MB だった。
- 1枚の画像に複数の種類をまとめる案は採らなかった。時間帯ごとに読み込み・解放する単位が種類ごとのほうが扱いやすく、1種類が小さくなったため。

### 10.9 ノックバックと状態異常（追加の技術検証2）
- 状態異常の種類は `data/game/status.json` に、効果の部品の組み合わせで定義する。今入っている部品: 継続ダメージ（`damagePerSecond`）、移動の速さの倍率（`speedMultiplier`。0 で止まる）、受けるダメージの倍率（`damageTakenMultiplier`）。これで、やけど・どく・まひ（遅くなる部分）・こおり・ぼうぎょダウンを表している。
- 敵ごとに「状態異常の種類 × 残りの更新回数」と「付けたプレイヤー」を型付き配列で持つ（`EnemyStore.statusTicks` / `statusBy`）。違う状態異常は同時にかかり、同じものを重ねたら残り時間の長いほうにする。
- ノックバックは「押し返す速さと時間」。止まっている敵にも効く。
- 技の性能に `knockback` と状態異常（`statusId` など）を持たせる（フェーズ1 区切り1 で仮の自動攻撃から技の定義へ移した。11.1）。
- 状態異常にかかっている敵は、その色で表示する（`status.json` の `color`。見た目だけ）。
- まだ部品が無い状態異常（`01_game_design.md` 4.6）: ねむり（ダメージで起きる）、こんらん（ふらふら動く）、まひの「ときどき止まる」、もうどく（時間とともに増える）、やどりぎ（攻撃したプレイヤーが回復）。いずれも同じ仕組みに部品を足せば作れ、同期の方式も同じでよい（ねむりの解除だけは、ホストからの知らせが要る）。

### 10.10 経験値の玉（追加の技術検証3）
- 玉は `GemStore`（`src/sim/entities/gems.ts`）に型付き配列で持つ。更新の順番では、発射体の命中・継続ダメージの後に「玉を落とす → 吸い寄せる → 拾う」を行い、最後に倒れた敵を取り除く（玉の位置に倒れた敵の位置を使うため）。
- 経験値は `world.xp` に全員共有の合計として持つ。レベルの計算とレベルアップの画面はフェーズ1で作る。
- 玉は青、まとめられて経験値が多い玉は赤で表示する（`data/render/placeholder.json`、`pickups.json` の `bigGemValue`）。

## 11. 実装メモ（フェーズ1）

### 11.1 データの土台と技の仕組み（区切り1）
- PokeAPI のデータは `npm run pokeapi`（`scripts/fetch-pokeapi.ts`）で `data/generated/` に生成し、**コミットする**（ビルドに通信を使わないため）。対象は `data/pokeapi/targets.json`。
- 技は `data/game/moves.json` に、キー（PokeAPI の技の名前）ごとに定義する。タイプと分類（物理・特殊）は PokeAPI から取り、手で書くのは「出し方」「見た目のレシピ」「レベル1の性能」「レベルごとの増分」だけ。最大レベルは増分の数 + 1。
  - 性能の項目: 威力・クールダウン・数・間隔・速さ・大きさ・距離・残る時間・貫通・当たり直しの間隔・ノックバック・状態異常（`src/data/schema.ts` の `moveStatsSchema`）。
  - 原作で変化技（status）に分類される技（やどりぎのタネなど）は、特殊の威力を使う。
- 出し方は区切り1で4つ: `nearest`（一番近い敵へ）・`facing`（向いている方向へ）・`melee`（前に一瞬の当たり判定。数が増えると後ろ・左右にも）・`orbit`（周りを回る）。残り（ビーム・扇形・飛んで戻る・設置など）は区切り2でたたき台の技を入れるときに足す。
- 当たり判定はすべて `ProjectileStore` で扱う（飛ぶ弾も、近接・周回のように持ち主に付いていくものも）。同じ敵に当たり直すまでの間隔を持てるよう、当てた敵の記録に「当てた更新番号」を加えた。
- ダメージ = 技の威力 × タイプ相性（`combat.json` の倍率。2タイプは掛け合わせて判定）× 状態異常による受けるダメージの倍率。ポケモンのステータス（物理・特殊の威力）は区切り3で掛ける。
- タイプ相性の表は、PokeAPI の今の世代の表を使う（フェアリーなど後の世代のタイプも含む）。
- `src/data/simRules.ts` が、data/ と PokeAPI のデータを組み合わせてシミュレーションの定義（`SimRules`）を作る。シミュレーションは技・タイプを番号で扱う。
- プレイアブルのポケモンと最初の技は `data/game/playables.json`。
- 確認用の URL: `?pokemon=bulbasaur`（ポケモン）、`?moves=ember:8,fire-spin:3`（覚えている技とレベル）。協力プレイでは参加用 URL に引き継ぐので2人とも同じになる（相手の技・ポケモンの同期はフェーズ3）。
- 仮の自動攻撃（`data/game/attack.json`）と、`?status=`・`?kb=` の上書きは廃止した。
- 見た目のレシピの `glowScale`・`coreScale` は「当たり判定の直径に対する倍率」に意味をそろえた。

### 11.2 レベルアップと選択（区切り2）
- 経験値は全員共有の `world.xp`。必要な経験値の表は `data/game/leveling.json` の `xpCurve`（base × レベル^exponent。区切り4で、強化なしで15分レベル50になるよう調整する）。
- レベルが上がると「選択を待つ数」が増え、選択中（`world.levelUp`）は**シミュレーションの更新を止める**（入力の状態と選択のコマンドだけ受け付け、時間・敵・技は進まない）。一度に複数上がったら、1回ずつ続けて選ぶ。
- 選択はコマンド（`chooseUpgrade`・`rerollUpgrades`・`skipUpgrade`）で行う。見送りと時間切れ（15秒）はリロール権 +1。再開時に全員へ短い無敵時間（`resumeInvincibleSeconds`。プレイヤーの HP は区切り3）。
- 候補の作り方（`src/sim/systems/leveling.ts` の `makeOffers`）:
  - 派生・固有技の条件（元の技が最大レベル ＋ 材料の持ち物。固有技は系統も）がそろっていれば必ず先頭に出す。
  - 残りは、技（自分のタイプとノーマルのタイプの技。枠が空いていれば新しい技、覚えている技の強化）・持ち物（枠が空いていれば新しいもの。持っているものの強化。タイプのアイテムは自分のタイプとノーマルのものだけ）から、シード付きの乱数で選ぶ。技は持ち物の `moveOfferWeight`（2）倍の重みで選ぶ。ほかの人が持っている持ち物も出る（07 19章）。
  - 派生先・固有技は直接は候補に出ない（`data/game/derivations.json` の `to` に出てくる技）。
- 派生すると元の技と入れ替わり、材料が「使うとなくなる」持ち物（石・つながりのヒモ。`items.json` の `consumable`）なら持ち物の枠から消える。
- 持ち物（`data/game/items.json`。`category` は stat・type・evolution）の効果は「1段階あたりの効果」の合計（`src/sim/upgrades.ts`）。威力（全体・物理/特殊・タイプ別）・範囲（全体・タイプ別）・クールダウン・発射の速さ・急所・移動速度・取得範囲・経験値・技の数（`amountBonus`）・持続（`durationPct`）を反映済み。技の数と持続は `attack.ts` の `playerMoveStats` で技のレベルの性能に足す。パッシブ（`passives.json`）は廃止した（07 21章）。HP・防御・回復・受けるダメージは区切り3で効く。
- 急所の倍率は `combat.json` の `critMultiplier`。急所の判定は当てたプレイヤーのブラウザの乱数で行う。
- 選択の画面は DOM（`src/scenes/levelUpPanel.ts`）。画面の横幅いっぱいに大きなカードを横に並べる。数字キー・クリックで選び、R でリロール、X で見送る（S は移動キーと重なるので使わない。押したまま開いたときのキーの自動の繰り返しは無視する）。カードには名前と短い説明だけを出し、派生の材料などのヒントは出さない。「おや……？」は、以前に一度達成した派生で、そのカードを取ると条件がそろうときだけ出す（達成の記録は `src/meta/discoveries.ts`。セーブデータができるまでブラウザに仮に保存）。見た目の作り込みはフェーズ4。
- 協力プレイでの全員同時のレベルアップと候補の配布はフェーズ3。今は協力プレイ中はレベルだけ上がり、選択は出ない。

### 11.3 技の出し方の追加（区切り2）
- たたき台（`07_content_draft.md`）の技28個をすべて `data/game/moves.json` に入れた（数値は仮）。
- 出し方を5つ足した: `beam`（直線。当たり判定は線分との距離）・`boomerang`（減速して戻る）・`ground`（敵の位置に残る。いなければ前方）・`nova`（自分を中心に広がる輪）・`homing`（一番近い敵を追う）。性能に `spreadDegrees`（向きのばらつき。360 でランダムな方向。かえんほうしゃ・あわ）と `lifestealPct`（吸収。HP は区切り3）を足した。
- 【初期案】（作者 2026年10月23日。体で当たる技・揺れの技の範囲が、ずっと自分を中心にした円なのは違和感がある）技の `sweep`（0〜1）で、当たり判定を**中心から外へ進む帯**にする。帯の厚さは届く距離いっぱいに対する割合で、帯が持続の間に中心から届く距離まで進み、帯より内側（通り過ぎた所）には当たらない。近接の扇形・自分の周り（`melee`）と広がる輪（`nova`）、じしんの続く揺れ（`wave`）で使える。塗り（HitShapes）も同じ帯だけを描く。たいあたり・のしかかり（0.45。持続を 0.2・0.24 秒に延ばした）・マグニチュード・じしん（0.3）に付けた。
- 【初期案】（作者 2026年10月23日）残る範囲（`puddle`）に `path` を足した: 円を並べて置かず、**通った道そのもの**を範囲（線の当たり判定）にする。ビームは線を1本。`every` で呼ぶ動く技は、元が通った道を線でつなぎ、まっすぐ進む間は1本を伸ばし、曲がったら次の線を足す。引き返してすでに残した道の上を通るとき（ブーメランの戻り）は足さない。道には発射体の芯を描かず、軌跡のパーティクルを線のあちこちから出す。ゴッドバード（燃える道）・れいとうビーム（氷の道）に使った。
- 【初期案】見た目のレシピに `ownerGhost` を足した: 発射体の芯の代わりに、持ち主のポケモンの姿を薄く描いて飛ばす（後ろに残像を連ねる）。ゴッドバード（ファイヤーの残像がブーメランのように飛ぶ）に使った。
- 【初期案】（作者 2026年10月23日。ピカチュウのリワーク）
  - 持ち物に `forms`（今の姿がこのどれかのときだけ持てる・効く）と `excludes`（一緒に持てない）を足した。でんきだまは `forms: ["pikachu"]`・`excludes: ["thunder-stone"]`。ピカチュウの `evolves: false` は外した。
  - ボルテッカー: 跳ね返り（`bounce`）の技にした。ピカチュウの残像（`ownerGhost`）が速く飛び、持ち主のまわりの枠の端で跳ね返り続ける。通った道は電気の範囲（`path`）になり、古い所から薄れて消える（通った道の範囲は、残り時間に合わせて塗りを薄くする）。跳ね返りは向いている方向から `bounceAngle`（35°）ずらして出し（乱数は使わない）、障害物は通り抜ける。強さの目安は跳ね返りをずっと当たり続ける見積もりにするので、ボルテッカーは調整の対象から外し、威力は前の 0.8 倍を手で決めた（何度も当たり、道も電気になる）。
  - 10まんボルト: 使うと同時に、自分の周りに電気の円（`cast` の残る範囲。半径 150・0.4 秒）を出す。見た目のレシピの `burstFlash` で、黄・黒・白の透けた塗りを 60 ミリ秒ごとに切り替えて光らせる。
  - かみなり（ライチュウの固有技）: 出し方は `scatter`（周りのランダムな場所）で、すぐ消える落雷。効き方の起こり方に `eachHit`（当たった敵ごとに、その敵の位置で起こす。どのブラウザでも起こす）を足し、落雷を受けた敵それぞれから `chain` で連鎖させる。固有技の派生に `forms`（今の姿がこのどれかのときだけ覚える）を足した（かみなりは `["raichu"]`）。見た目のレシピに `bolt`（上からジグザグの稲妻を落とす）を足し、落雷の円は `burstFlash` で光らせる（`burstFlash` は効き方から出た円だけでなく、技の円にも効くようにした）。
- 【初期案】（作者 2026年10月23日。コインで買えるポケモン。`07` 29章）
  - ショップの `pokemon`（キーと値段）。買うとセーブの解放済み（`unlocked`）に足す（`buyPokemon`）。

  - 見た目のレシピに `chargeGlow` を足した: 技の再使用の残りが `seconds` を切ると、持ち主の後ろの光と、体の形をその色で光らせる重ね絵を、出す直前ほど強く出す（ギガインパクト）。

- オーラ（ねむりごな・はなびらのまい）は `melee` の `range: 0`（自分の周り全体）で表す。突進（フレアドライブ・でんこうせっか）は、今はプレイヤーを動かさず近接・高速の発射体で代わりにしている（プレイヤーごと動かすかは要検討）。
- 状態異常を3つ足した: ねむり（止まる。ダメージを受けると治る。継続ダメージでは治らない）・ひるみ（ごく短く止まる）・やどりぎ（継続ダメージ。付けたプレイヤーの回復は区切り3）。
- 見た目のレシピは、タイプの基本（fire / water / grass / poison / flying / normal）を技ごとに extends している。当たり判定が大きい技（なみのり・ヘドロばくだんなど）は光の倍率を小さくしている。直線（ビーム）は光の画像を線の長さに引き伸ばして描く。

### 11.4 プレイヤーと進化（区切り3）
- ステータスは `data/game/stats.json`。ゲーム内の値 = 基準値 × 種族値のランクの倍率 × レベルの伸び（`perLevelPct`）× 持ち物（`src/sim/species.ts` の `deriveStats`、`leveling.ts` の `recomputeModifiers`）。
  - 最大HP（種族値 HP）・物理/特殊の威力（こうげき/とくこう。技のダメージに掛ける倍率）・防御（ぼうぎょ・とくぼうの高い方）・移動速度（すばやさ。`player.json` の値を基準にランクの倍率を掛ける）。
  - 受けるダメージ = ダメージ × 100 / (100 + 防御) × (1 + 受けるダメージの倍率)。
  - レベル・持ち物・進化で作り直す。最大HPが増えた分は今の HP にも足す。
- 雑魚の接触ダメージは `enemies.json` の `contactDamage` × 時間帯の `damageMultiplier`（出現した時点の値を敵ごとに持つ）。触れたかは自分のブラウザで判定し、重なっている敵のうち一番大きいダメージを1回受けて、無敵時間（`hurtInvincibleSeconds`）に入る。
- HP の回復: たべのこし（毎秒）・吸収（ギガドレインなど。与えたダメージの割合）・やどりぎ（継続ダメージの分）。自分の HP は自分のブラウザで管理するので、回復も自分の分だけ。
- HP が無くなると、全員で共有の復活可能数（`stats.json` の `revive.initialCount`。永続強化で増やす）を使って自動で復活する（ソロ）。無ければ倒れて、動かず技も使わない。ランの失敗と結果画面は区切り4、協力プレイの「触れて復活」はフェーズ3。
- 進化（`src/sim/systems/evolution.ts`）: PokeAPI の進化の条件から作る。レベル（原作どおり）・石（持っていれば進化して石はなくなる）・通信交換（つながりのヒモ）。進化するとタイプ（技の候補）とステータスが変わり、見た目のスプライトを途中で読み込んで差し替え、光の演出を出す。
- ポケモンの種類は `data/generated/pokemon.json` のすべてを `SimRules.species` に入れる（プレイヤーのポケモンを番号で指す）。
- 足元に HP のバーを出し、無敵時間の間は点滅、倒れたら暗くする。相手のプレイヤーの HP は同期していないので出さない（フェーズ3）。
- 確認用の URL: `?level=15`（そのレベルから始める）。
- スプライトの作者が SpriteCollab の名前の一覧に無い場合は、Discord の ID を載せず「Unknown (Discord)」とする。

### 11.5 ランの流れ（区切り4）
- マップの選択（`RegionScene`。DOM。作者の案 2026年10月22日）: タイトルの「ソロ」「マルチ」の次の画面。地方を 3×3 のカードで並べ、遊べる地方はプレイアブルの数と最初の3匹のアイコン、遊べない地方は「Coming soon」を出す。クリック・矢印キーで選び Enter で決める。ソロはポケモン選択へ、マルチは部屋を作って待合室へ進む。地方の並び・遊べるか・地方ごとのプレイアブルは `data/game/regions.json`、名前は PokeAPI（`data/generated/regions.json`）。出てくるポケモン（`stage.json`・`spawn.json`）は今はカントーの分だけで、2つ目の地方を作るときに地方ごとに分ける。
- ポケモン選択（`SelectScene`。DOM）: 選んだ地方のプレイアブルだけを並べる。Esc でマップの選択に戻る。 クリック・矢印キーで選び、ダブルクリック・Enter・「はじめる」でランを始める。最初は一覧の先頭の解放済みのポケモンを選んでおく。下にマウスを乗せている（無ければ選んでいる）ポケモンの名前・タイプ・最初の技を出す。
- 画面: タイトル（`TitleScene`）→ マップの選択（`RegionScene`）→ ポケモン選択（`SelectScene`）→ ラン（`RunScene`）→ 結果（`ResultScene`）。結果画面から「もう一度」で同じポケモンのランを始め直す（`RunScene.init` で前のランの状態を消す）。協力プレイ（`?host`・`?join=`）と `?pokemon=` のときは、タイトルを飛ばしてすぐにランを始める。
- ステージの定義は `data/game/stage.json`: ランの長さ（15分）、中ボスの出る時間と種類、ボスと範囲技、中ボス・ボスの共通の決まり。中ボス・ボスは `enemies.json` の敵の種類に `rank`（midboss / boss）を付けて定義し、`species` で見た目と名前のポケモンを指す。
- 中ボス・ボスも雑魚と同じ入れ物（`EnemyStore`）で持つ。予定の時間になったらプレイヤーの近くに出し（`src/sim/systems/stage.ts`）、HP は参加人数で増やす。前の時間帯の種類でも消さない。ノックバックを受けず、動きを止める状態異常の時間は短くする。

### 13.2 雑魚の HP と区間の進行（作者のテストランを受けて。2026年10月21日）
- 雑魚の HP = 種類の HP（7）× 区間の倍率 × (1 + `hpPerLevelPct` × (レベル − 1) / 100)（`enemyHpScale`）。出したときのレベルで決まる。スウォームも同じ。中ボス・ボスは今までどおり固定（人数で上げる）。
- 区間: `world.section` と `sectionStartTick`。`currentWaveIndex` は区間の番号を返す（時刻ではない）。中ボス・ボスの予定は `stage.json` の `wave`（区間）と `afterSeconds`（区間が始まってから）。`gate` の付いた中ボスがすべて出て倒れたら、次の区間へ進む（`advanceSection`。ソロ・ホスト）。中ボスのいない区間（チャンピオンロード）は `durationSeconds` で進む。最後の区間（四天王）からは進まない。
- 協力プレイ: ホストが区間を進めたら `sa` で送り、ゲストは `setSection` で合わせる。
- 地面のタイル（`ground.json` の `waves`）は区間と同じ並び・同じ数にした（`startSeconds` をやめた）。スプライトの先読みは、中ボスが出る少し前（または区間の残り時間）から次の区間の分を読む。
- 確認用: `?section=3` でその区間から始める（`?time=` は時刻だけ進める）。
- `npm run balance`（自動のプレイヤーは中ボスを狙わないので、倒すまで 10〜30秒かかる）: 区間はおよそ2分ごとに進み、四天王の区間は16〜17分台に始まる。11系統のうち10系統がクリア（ケーシィは四天王が残って失敗）。

### 13.3 ビリリダマのじばく・重なりの表示順（作者のテストランを受けて。2026年10月21日）

### 13.4 技の当たり判定の縁取り（作者の指摘。2026年10月21日）
- 光の演出（`EffectRenderer`。光の画像とパーティクルを重ね、ドット絵風のフィルターを掛ける）には当たり判定の輪郭が無く、当てている感じが少ない、という指摘。当たり判定の形（円・両端の丸い直線）の外周を、スプライトと同じ大きさのドット（2）で描く（`HitOutlines`。明るい線はレシピの光の色、外側の暗い線はその 0.35 倍）。フィルターの外で、ふつうの合成で上に重ねる。
- 【初期案】まずヒトカゲの系統の技だけで試す（`sprites.json` の `hitOutline.moves`。省略すると全部の技）。
- → 作り直した（作者の指摘。2026年10月21日）: 外へ向かって薄くなるグラデーションの端まで縁取ると、見づらかった。**当たり判定の範囲はグラデーションで表さない**ことにし、当たり判定の形（円・両端の丸い直線・扇形）をそのままの大きさで**平らに一色で塗り**、外周に明るい線を1本引く（`HitShapes`。暗い縁取りは廃止）。塗りはレシピの光の色、線はそれを白へ寄せた色。角ばったドットにするフィルターを掛ける。設定は `sprites.json` の `hitShape`（`pixel`・`fillAlpha`）。
- → 外周の線もやめた（作者の指摘。2026年10月22日）: 輪郭を強調するとかえって見づらかった。グラデーションをやめたので塗りの端がそのまま当たり判定の端になり、線が無くても範囲が分かる。当たり判定の形を一色で塗るだけにした（`edge`・`edgeAlpha`・`edgeLighten` は削除）。
- 近接の扇形（`SHAPE_SECTOR`）は、当たり判定は扇形全体のまま、見た目は**弧の近くの帯（バームクーヘン型）**だけを描く（360° なら輪）。帯の太さは半径の `sectorBand`（0.3）。扇形を塗りつぶすと目にうるさい、という作者の指摘（2026年10月22日）。
- 光の演出（`EffectRenderer`）は、当たり判定からはみ出す光（`glowScale`）を描かず、発射体の**芯**（縁のはっきりした小さな円。当たり判定の直径 × `coreScale` × 0.35）だけを描く。軌跡・命中のパーティクルはこれまでどおり。

### 13.4.3 見える範囲（作者の決定。2026年10月22日。`07` 25章の B 案）
- 見えるワールドの縦の広さを、どの端末でも `camera.viewHeight`（720）にそろえる（拡大率 = 画面の高さ ÷ 720。丸めない）。横は端末の比率に合わせて広げるが、`maxAspect`（16:9）まで。それより横長なら、ランの画面ではゲームの描く面（canvas の親の `#game`）の幅を 16:9 に縮めて真ん中に置き、左右を黒い帯にする（ほかの画面に移るときに画面いっぱいに戻す）。
  - はじめはカメラの描く範囲（viewport）を真ん中に狭めていたが、フィルターを掛けた技の光（`EffectRenderer`）と範囲（`HitShapes`）だけが帯の幅だけ左にずれた（作者の指摘 2026年10月22日。技の出どころが自分より左にずれる）。カメラはずらさないようにした。canvas の大きさを変えるのは次のフレームで行う（resize の処理の途中で変えると、元の大きさで上書きされた）。
- 技の範囲の色（作者の指摘 2026年10月23日）: スモッグは濃い紫、ねむりごなは薄い白（以前は逆の印象だった）。ハードプラントは、はっぱカッターと同じ緑をやめ、焦げ茶の範囲・土の色の細い筋・土くれが落ちるはじけで、根っこが地面をえぐる演出にした（`data/effects/recipes.json`。演出の光は足し合わせなので、暗い色は範囲の塗りで出す）。
- 重なりの順（作者の決定 2026年10月22日、23日に変更）: プレイヤー ＞ ボス（中ボス・ボス・伝説） ＞ 技 ＞ 雑魚 ＞ アイテム。障害物（岩・木）はアイテムより奥。値は `data/render/sprites.json` の `depths`。以前は技の光がプレイヤーより手前で、落ちているアイテムが敵より手前だった。
- 画面に固定する HUD は `placeUi` で拡大率を戻して置くので、端末に関係なく同じ px の大きさ。地面のタイルは `GroundTiles.fit` でカメラの描く範囲に合わせる。

### 13.4.2 進化で増える効き方の部品（07 22章。2026年10月21日）
- 出し方 `stream`: 持ち主に付いていく直線（`MOTION_STREAM`）。向いている方向から `angle` だけずらした向きへ、`angularSpeed`（技の `speed` を 度/秒 として使う）の速さで回る。長さは毎回、障害物の手前まで（最大 `orbitRadius` = 射程）。残り時間は再使用の時間なので、途切れずに出し続けて見える。
- 技の定義の `effects`（効き方の部品。`src/sim/systems/moveEffects.ts`）: `trigger` で起こるとき（`cast` 技を使ったとき・`hit` 当たり判定が初めて敵に当たったとき・`end` 消えたとき/落ちたとき・`every` 残っている間 `everySeconds` ごと。流れは流れが最初に当たる敵の位置）を決め、部品を組み合わせる: `explode`（爆発。`delaySeconds` で印を置いて遅れて弾ける・`pull` で中心へ引き寄せる）・`puddle`（残る範囲。直線なら `alongSpacing` ごとに並べる）・`split`（分裂。`boomerang` で戻る）・`chain`（連鎖）・`orbit`（周回）・`spikes`（突き出す直線）・`wave`（広がる輪）。大きさ・威力は元の当たり判定の倍率。
- 効き方から出た当たり判定は `stage` 1（さらに効き方を起こさない）、遅れて弾ける印は `stage` 2（当たりの判定をしない）。ノックバックの上書き（`knockback`。マイナスで引き寄せ）も当たり判定ごとに持つ。確率（`chance`）は共有の乱数ではなく時刻と位置のハッシュで決める。
- 技の定義の `curve`（度/秒）: 飛ぶ弾の速度の向きを回す（ふぶき・エアスラッシュの渦）。広がる輪（`growth`）は、その場に置いた当たり判定でも使える。
- 状態異常に `soaked`（ぬれ。遅くなる。なみのり）を足した。

## 14. 音（フェーズ4）

- `src/audio/`。シミュレーションからは使わず、画面の側で出来事を見て鳴らす（`RunSounds`）。
- 効果音（`Synth`）: Web Audio で矩形波（幅 12.5/25/50%）・三角波・のこぎり波・雑音を鳴らす。音ごとの部品は `data/audio/sfx.json`（音の高さの動き・長さ・遅れ・音量）。同じ音を続けて鳴らす最短の間隔と、同時に鳴る数の上限で、大量に倒しても割れないようにする。経験値の玉は続けて拾うと半音ずつ上がる。ふしぎなアメなどで続けてレベルが上がると、レベルアップの音を少しずつずらして続けて鳴らす。
- 技を使う音は、技を使ったときの出来事 `moveUsed`（自分のぶんだけ鳴らす）とタイプで選ぶ（`move.<タイプ>`）。テストで、すべての技のタイプに音があること、コードで鳴らしている音がデータにあることを確かめる。
- BGM（`BgmPlayer`）: `data/audio/bgm.json` の曲を HTML の audio で鳴らし、曲が変わるときは前の曲を小さくしながら次を大きくする。ファイルが無い曲は鳴らさない。区間ごとの曲（`run.sections`）、伝説戦、タイトル、結果画面。
- 音量（全体・BGM・効果音・ミュート）はブラウザに保存（`AudioSettingsStore`）。タイトルの O で設定の画面、ラン中は M でミュート。ブラウザの決まりで、最初のクリックかキーの後から鳴る。
- BGM は楽譜（`data/audio/music`）をコードで鳴らすこともできる（`MusicPlayer`: 少し先までの音を予約し続けてループ。効果音と同じ AudioContext を使い、曲ごとのゲインで音量とフェードを変える）。`bgm.json` の曲は file か score。
