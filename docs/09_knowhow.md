# 09. ノウハウ（ジョウト地方のローンチ前のまとめ）

カントーの内容とバランス調整（フェーズ4）で分かったことを、次の地方（ジョウト）を作る前にまとめる。仕様そのものは `01`〜`07` が正で、ここには「どう進めるとうまくいったか・どこでつまずいたか」を書く。2026年10月25日 時点。

## 1. 地方を足す手順（チェックリスト）

ジョウトは `data/game/regions.json` に `available: false` と解放の条件（伝説のミュウを倒す。`unlock: { stat: "bossDefeated.mew" }`）だけが入っている。作るときは次の順に進める。

1. **出てくるポケモンを決める**（作者に確認）: ジムリーダー8人の相棒（中ボス）・四天王（大ボス）・伝説・区間ごとの雑魚・プレイアブルの系統。決めたら `07_content_draft.md` に表を作る。
2. **PokeAPI の名前とデータ**: `data/pokeapi/targets.json` の `pokemon`・`moves`・`items` に足して `npm run pokeapi`。キーは PokeAPI の名前（例: たいりょくのハネは `health-wing`。間違えると 404 で止まる）。取得はキャッシュ（`scripts/.cache/`）されるので何度実行してもよい。
3. **ドット絵**: `npm run sprites`。雑魚だけのポケモンは歩きだけの軽い画像（`uses: ["enemy"]`）、プレイアブル・ボスは全動作（`uses: ["full"]`）。足りない動作は報告に出る。クレジット（`public/sprites/credits.json`）は自動で作られる。
4. **区間と雑魚**（地方のステージ `data/regions/<地方>.json` の `sections[]`。`02` の16章。区間ごとに `wave`・`tile`・`bgm`・`obstacles`・`night` を1か所に書く）: 区間は「中ボスを倒すと次へ」（中ボスの無い区間は `wave.durationSeconds`）。1つの場所の途中で場面を変えたいときは区間を2つに分ける。同じ種類を、間を空けて別の区間にまた出すときは別の敵 ID にする（例: `hoothoot-2`。一度いなくなった種類は戻せない検証がある）。雑魚の種類・出現の速さ・最低数・上限・`hpMultiplier`・`damageMultiplier`・`xpMultiplier`。~~中ボス・ボス・伝説・スウォームに出るポケモンと**その進化前**は雑魚に出せない（読み込み時の検証でエラー。例外は `allowBossSpecies`）。~~ → 2026年10月27日にこの縛りは無くした（07 の60章。解放の条件が「ボスを倒す」に変わったので不要）。検証も外した（J2）。
5. **ボス**（地方のステージの `bosses`・`legendary`・`swarms`、範囲技の一覧は全地方で共通の `stage.json` の `moves`、`enemies.json` の HP。ほかの地方と種族が同じボスは `johto-` などを付けた別の ID）: 中ボスは `gate: true`（倒すと区間が進む）、四天王は段階的な大ボス（`enrage` で第2段階）。伝説は `legendary.moveSets` で伝説ごとの技と間隔（`moveIntervalSeconds`・`enrageMoveIntervalSeconds`）。
6. **プレイアブル**（`playables.json`・`regions.json` の `playables`）: 最初の技、`fixedMoves`（技を覚えない）、`itemMoves`（持ち物で技を覚える）、`unlock`（解放の名前）。解放は実績（`achievements.json`）かショップ（`shop.json` の `pokemon`）。
7. **技と派生**（`moves.json`・`derivations.json`）: 7章の作り方を参照。技を足したら `npm run balance-moves` と `npm run moves-table`（`08` は手で直さない）。
8. **見た目**: 技のレシピ（`data/effects/recipes.json`）、技のドット絵（`src/render/moveArt.ts`）、技のアイコンの絵柄（`data/render/icons.json` の `moveGlyphs`。無ければ出し方の絵柄）、地面・障害物。
9. **ショップ・実績**（`02` の17章）: 地方の実績は `achievements.json` に `region` を書く（条件の記録の名前はカントーと同じでよい。判定はその地方の記録だけ）。売るポケモンは `shop.json` の `pokemon` に `region`。ショップの解放の条件は `shop.json` の `regions.<地方>.unlock`、案内の文は `shop.unlock.<地方>`。
10. **文章**: 翻訳ファイル6言語（ja・en・fr・de・es・it）。ポケモン・技・持ち物・タイプ・地方の名前は PokeAPI から出す（翻訳ファイルに書かない）。
11. **確かめる**: `npx tsc --noEmit`・`npx vitest run`・`npm run balance`・ブラウザ（8章）。作っている間は、地方の選択に `?regions=all`（開発版だけ）でその地方を選べる。`?section=<番号>` でその区間から始められる。地方を `available: true` にするのは最後。

## 2. バランス調整の進め方

### 2.1 まず参考作品の値を調べる
速さ・出現の量・難しさは、ヴァンパイアサバイバーズ系の常識に合わせる（プレイヤーは敵よりずっと速い、圧力は量、序盤はゆっくり）。逆向きの調整をして作者から指摘されたことがある。値を変える前に参考作品の実際の値を調べ、報告では「変えた向き」が狙いと合っているかを確かめる。

### 2.2 数字で測る（`npm run balance`）
`src/sim/run.balance.ts` が、倒れない自動プレイヤーで1ランを通しで回し、系統ごとに次を出す。

| 出る値 | 見ること |
|---|---|
| 分ごとのレベル・撃破数 | 成長の速さ（強化なしで 15分にレベル50前後が目安だった） |
| 区間が進んだ時刻 | 中ボスに手間取っていないか |
| 区間ごとの敵の数（平均） | 群れの圧力 |
| 区間ごとの雑魚の HP の倍率 | 時間帯・ジム・レベルを掛けた実際の倍率 |
| **雑魚が近くに来てから倒されるまで（秒）** | 雑魚の固さ（歩いてくる時間を除くため、プレイヤーから 250 以内に来てから数える） |
| **ボスを倒すまで（秒）** | 中ボス・四天王・伝説の手応え |

- 「出てから倒されるまで」は歩いてくる時間（約14秒）がほとんどで、固さの目安にならなかった。近くに来てからの秒数にして初めて違いが見えた。
- 雑魚の HP を区間ごとに上げる前は、終盤でも 1.5〜3 秒でほぼ平ら（範囲技のダメージが HP を大きく上回る）。最後の区間の倍率を ×3.2 → ×18 にして、序盤 1〜3 秒 → 中盤 3〜5 秒 → 四天王 6〜10 秒の右肩上がりになった（`01` 雑魚の HP の項）。
- 自動プレイヤーは倒れないので「生き残れるか」は測れない。また技の選び方が単純なので、ワンリキーのように組み立てが要る系統は極端に弱く出る（ワンリキーは自動ではほぼ進めない）。ゼニガメは逆に強く出る。数字は傾向として見て、最後は作者の手触りで決める。
- 全員分は時間がかかるので、`-t "charmander|squirtle|..."` で系統を絞って回す。
- 地方と永続強化の段階: `BALANCE_REGION=johto BALANCE_UPGRADES=3 npx vitest run --mode balance --silent=false -t "cyndaquil"`（その地方のプレイアブルを回す。強化は全部その段階まで。07 の86章）。

### 2.3 技の強さは帯でそろえる（`npm run balance-moves`）
- 総合の強さ = √(単体 × 群れ)（`src/data/moveStrength.ts`）。段階ごとに最大の強さの帯がある（タイプの技 80・派生技 240・固有技 600。`move-balance.json`）。スクリプトは威力だけを書き換え、範囲・数・速さは変えない。
- 帯から外す技は `exempt`。最大レベルを他と変えた技（ばくれつパンチ Lv16）は、帯に入れると途中のレベルが弱くなるので外した。
- 数が増えるレベルでは、1発の威力が下がる（増分がマイナス）ことがある。

### 2.4 決めてある関係
- 伝説は最後の大ボス（ワタル）より強い。四天王の HP を上げたときも、ワタルと伝説は据え置いた。
- ショップの全部の費用は「クリア何回分か」で見る（今は約18万コイン、クリア約100回分）。値段を変えたら、前の値段で買った人へ全額返す（`shop.json` の `repriced`。新しい値段で払い戻すと多すぎ・少なすぎになる）。

## 3. 作者とのやり取りで分かった好み

- 名前は**原作で使われる言葉**か**ゲーム内の用語**にする。ほかのゲーム由来の言葉（アーマー・グリード など）は避ける。ショップの強化は、道具の名前ではなく こうげきりょく・ぼうぎょりょく のような言葉が選ばれた。
- 技の手触りは、作者が技の見本帳で遊んで1つずつ指摘する。指摘は「見た目の動き」で来る（例: 「いわおとしのように降る」「蛇行して先で弾ける」）。既存の技の動きの部品を組み合わせて応えるとよい（7章）。
- 弱すぎる技は「リワーク」、強すぎる技は再使用を延ばす・数を減らす、の形で頼まれることが多い。
- 進化で使った技は候補に出さない、材料にした技の強化は受け継ぐ、など「育てた分が無駄にならない」形が好まれる。
- 【決定】【要決定】の印のある所は、仮に作らずに先に聞く。どちらでもよい細部（消費するか・残すか など）は、作って試せる形にしてから選んでもらうと早い。

## 4. 技の作り方

- 技は「出し方（`pattern`）× 効き方（`effects`）× 見た目（レシピ）」の組み合わせ。新しい技は、まず既存の部品で作れないかを考える。
  - 出し方の例: facing・nearest・homing・melee・orbit・beam・stream・lob・strike・chain・bounce・scatter・cross・sweep・spiral・pulse・weather・barrage・screen・nova・eruption・spin・rest。
  - 効き方の部品: explode・puddle（`path` で通った道）・split（`lob`・`snake`・`jitter`）・chain・orbit・spikes・cluster・crack・wave。起こるとき（trigger）は cast・hit・end・every・eachHit・spawn。
  - 姿で変わる効き方は `forms`（しんそく: ウィンディなら炎）。
- 派生（`derivations.json`）の形: 元の技（最大）＋ 持ち物 → 派生技。固有技は系統（`line`）付き。追加の条件は `minLevel`・`forms`・`withMoves`（ほかにも最大で持つ技。進化で消費）・`consumes`（持っていれば消費）・`inheritLevels`（材料の強化分を受け継ぐ）。
- 消費した技は `consumedMoves` に入り、もう候補に出ない。
- 技のドット絵（`moveArt.ts`）のパレットの番号は 0〜9 の1文字。10色を超えると行がずれて検証に落ちる。
- 技のアイコンの絵柄は 12×12 の塗りを書けば、縁は自動で付けられる（作ったときのスクリプトの考え方: `#` の隣の空きを `+` にする）。

## 5. 協力プレイで気を付けること

- ソロ・ホストが決め、出来事（events）を通信（`src/net/sync.ts`）でゲストへ送り、ゲストはコマンドとして当てはめる。**新しく状態を足したら、ゲストへの送り方も一緒に作る**（例: マップの箱は `bs`・`br`、ポーズは `pz`）。
- 他のプレイヤーの技の当たり判定は、どのブラウザにも見た目として存在するが、**狙いや落ちる場所は本人の画面とずれる写し**。当たったかは、ダメージも箱も**当てた人のブラウザで判定してホストへ伝える**（箱をホストの画面だけで数えたら、ゲストが当てても開かない不具合になった）。
- 協力プレイの不具合は、ホストとゲストの状態を通信の遅れの分だけずらして比べる長いテスト（`src/net/boxFuzz.test.ts`）で探すとよい。
- 「同じ回か」をレベルの数で区別しない。最大レベルの後はレベルが同じまま回が続き、自動選択が2回目を選ばずに時間切れまで待つ不具合になった。回には通し番号（`levelUp.serial`）を使う。
- ゲーム全体を止めるもの（レベルアップ・ポーズ）はシミュレーションの中で止める。演出のためにローカルだけ止めてよいのはソロだけ（進化の演出・スマホの縦向き）。
- 組み込みのブラウザは裏のタブを止めるので、2つのタブでの協力プレイの通しの確認はできない。通信はテスト（`src/net/sync.test.ts`）と、待合室でのメッセージの往復で確かめる。

## 6. 確かめ方（ブラウザ）

- 確認用の URL: `?pokemon=X&moves=key:lv,key:lv&level=N&spawn=N&time=秒&debug`。`?pokemon=` はそのポケモンを遊べる最初の地方で始まる（`?region=johto` でも選べる）。
- **テストプレイ**（作者の依頼 2026年10月26日。ソロだけ）: `?legend=mewtwo`（mewtwo・mew・articuno・zapdos・moltres・charizard（色違い）など）で最初から伝説と戦い、`?god` で無敵になる。無敵の間に受けたはずのダメージの合計と、最大 HP の何回分かを画面の上に出す。どちらかを付けたランは**記録を保存しない**（コイン・実績・解放が進まない）。例: `https://pokeswarm.org/?pokemon=charmander&level=60&moves=blast-burn:8,flare-blitz:8,flamethrower:8,fire-spin:8&legend=mewtwo&god`
  - ジョウト（07 の85章）: `?region=johto&legend=red-pikachu`（レッド戦の1ラウンドから。`red-espeon` で2ラウンド、`red-charizard` で3ラウンド）、`&wings` を足すとはねを持っていて、レッドに勝つとルギア → ホウオウ。`?legend=lugia`・`?legend=ho-oh` でその1戦だけ。`?intruder=raikou`（entei・suicune）で三犬が乱入する（`&time=300` などと一緒に）。どれも記録を保存しない。
- **開発版だけの ?restore=50000**（作者の依頼 2026年10月27日）: 伝説以外の実績を全部達成にし（報酬のポケモンも解放）、コインを少なくともその数にして、すぐ保存する。公開版のビルドには入らない（`import.meta.env.DEV`）。localhost も本番と同じ Firebase につながるので、Google でログインしてから開くと、そのアカウントのセーブに入る。
- 開発サーバーではモジュールをその場で読み込める: `await import('/src/sim/systems/boxes.ts')` で関数を呼び、`window.game.scene.getScene('run')` でシーンを触る。
- 画面が隠れているとき: `sc.scene.pause()` してから `sc.runSteps(n, true)`・`sc.draw(...)` で進める。
- スクリーンショットは演出に遅れることがある。DOM の変化は `MutationObserver` で回数と時刻を数える方が確か。
- 隠れている画面では `requestAnimationFrame` が止まる。DOM の演出の切り替えは `setTimeout` にする。

## 7. 作業の落とし穴

- **セーブを消さない**（作者の報告 2026年10月27日: テストのランの後、アカウントのデータが全部リセットされた）。原因の道筋: 開いた直後にランを始めて重くなり、Firestore の読み込みが 10 秒で間に合わない → 空のデータを作って「自分の一時保存」としてブラウザに書く → 次に開いたとき「ブラウザの方が新しい」として Firestore を空で上書き。直した決まり（`src/meta/saveStore.ts`）: 読めず一時保存も無いときの空のデータは「仮」でどこにも書かない／ログインする前の変更でログインしていた人の一時保存を上書きしない／何も進んでいない空のデータは進み具合のあるデータを上書きしない。`?pokemon=` で開いたときは、セーブの読み込みが終わってからランを始める。セーブの仕組みを変えるときは、`src/meta/saveStore.test.ts` の「セーブを消さない」のテストを必ず通す。

- `node -e` の中のバッククォートはシェルに解釈される。書き換えのスクリプトは Write で `.cjs` に書いてから実行する。
- `JSON.stringify` で JSON を書き直すと書式が変わる。行単位・文字列の置き換えで直す。
- Markdown の表の途中に行を足すと表が切れる。表の後ろに書く。
- Phaser のシーンは作り直さずに使い回すので、クラスのフィールドの初期値は2回目のランで戻らない。ランごとの状態は `init()` で戻す（回復とコインの自動選択が次のランに残った）。**絵（GameObject）を入れておく Map・配列は特に注意**: 前のランの絵はシーンを閉じたときに壊れるので、持ち越すと触った瞬間に例外になり、描画が止まる（箱の☆のアイコン）。協力プレイではタイマーでゲームが進み続けるので「画面だけ止まる」に見える。
- 描画の例外は、ページの中で `window.game.step(t, 33)` を try/catch で回すと捕まえられる。協力プレイの描画は、偽の通信路（`transports` に送ったものを配列にためるだけのもの）とゲストの Simulation・SyncSession を同じページで動かせば再現できる（1つ目のランの後に、もう一度ランを始めて試す）。
- `placeUi()` は倍率も上書きする。位置を決めてから `setScale` する。
- prettier は使わない。コミットは pokeswarm-dev（noreply のメール）で、個人のメールを載せない。

## 9. ジョウトで分かったこと（ホウエンの前のまとめ。2026年10月27日・版 0.5.1）

ジョウトは `10_johto_kickoff.md` の J0〜J6 の順で1日で作れた。ホウエンも同じ形（指令所の文書 → 確認 → 区間 → 土台 → ショップ・実績 → プレイアブル → ボス → 仕上げ）で進めるとよい。

### 9.1 進め方
- **最初に指令所の文書を作る**（`10` の形: 読む順・いまの状態・作業の順番・作者に聞くこと・守ること）。新しいコンテキストはそこから始める。
- **確認はまとめて、案を付けて聞く**。作者は「概ね OK、ここだけ直す」で答えることが多い（85章: クリアの時点・はねの条件・HP・セレビィ）。★ で決めてほしい所を絞り、ほかは【初期案】で進める。
- **プレイアブルの技は表で案を出す**（07 の80章）。作者が表に直接直しを書いてくる（初期技・覚える技・固有技の材料）。
- **作者が出先のときは localhost を見られない**。組み込みのブラウザで画面を撮り、ファイル名を技の名前にして送る（SendUserFile）。止まった写真では回る・伸びる・突き出す動きが分からないので、そう書き添える。
- 区切りごとに版を上げる。地方を公開したら真ん中の数字を上げる（ジョウトで 0.5.0）。push は毎回作者に聞く。

### 9.2 地方ごとに分けたもの（ホウエンでもそのまま使える）
- ステージ: `data/regions/<地方>.json`（区間・ボス・スウォーム・伝説戦・乱入・曲）。区間ごとの昼夜（`night`）。
- 記録・解放・実績・強化: 記録は `<地方>:` を付けて別に数える（`regionScope.ts`）。解放は `regionUnlockKey`、実績は `region`、ショップは地方ごと（解放の条件は `shop.json` の `regions`）。**ほかの地方の強化は効かない**（58章）。
- 同じ種族でも地方ごとに別の敵 ID（`johto-boss-machamp`）・別の解放。進化の持ち物も地方の実績で出す（カントーにジョウトの持ち物を出さない）。
- ほかの地方の種族を遊べるようにすると、**その地方に絵の無い進化先へ進化してしまう**（カントーのイワークがハガネールへ）。進化先は全部の動きの絵（`uses: full`）がある種族だけにしてある。足すときは `data/sprites/pokemon.json` に `full` を付ける。

### 9.3 ジョウトで足した仕組み（ホウエンで使い回せる）
- **進化**: なつき（歩いた距離 `friendshipDistance`）・時間帯（`time: day|night`）・持ち物の交換進化は持ち物の進化に読み替え（`fetch-pokeapi.ts`）・進化を聞いてキャンセル（移動をたくさん入れる。`answerEvolve`）・系統のルール（`SimRules.lines`: 姿ごとの技 `formMoves`・変わる先 `becomes`・HP を使う技・覚えないタイプ `excludeMoveTypes`）。
- **タマゴ**: 抽選してかえる（`hatch.ts`。協力プレイは部屋のシードで決まる）。ベイビィの涙など、絵に無い動きは自作のドット絵を重ねる。
- **伝説戦の形**: 続けて戦うラウンド（`rounds`。何体も同時に出せる。ラウンドごとの曲・記録 `stat`）・条件付きの続きの戦い（`bonusRounds`。はね）・ランの途中の乱入（`intruders`）。クリアの時点は `required` のボスで決まる。
- **マップの効果**（`legendFieldSchema`）: 風で流す `wind`・タイプの威力を変える `typePowerPct`・遅くなる・削る・凍る・オーラ・天気・落雷・明滅。ボスの範囲技の回復 `healPct`。ホウエンのグラードン（日差し）・カイオーガ（雨）・レックウザ（天気を消す）はこの部品で作れる。
- **技の部品**: 置いてから待つ `scatterDelaySeconds`（空から落ちる塊 `fall`）・当たるほど大きくなる `growOnHit`・雨でタイプの威力 `rainBoost`・回復の円 `healZone`・味方の回復 `allyHealPct`・向いている方へ出すビーム `aimFacing`。
- **技の絵**: 向きで描き分け（`directional`。正面・横・斜め）・突き出す1枚（`fit: thrust`）・天気の粒の絵（`weather.texture`。白黒で描いて色を付ける）・空から落ちる絵と破片（`fall`）。
- **確かめ方**: `?legend=red-pikachu`・`?wings`・`?intruder=raikou`、強さの測り方は地方と強化の段階を選べる（`BALANCE_REGION`・`BALANCE_UPGRADES`）。

### 9.4 落とし穴（ジョウトで踏んだもの）
- **派生技の強さの検証**（`moveStrength.test.ts`: 派生技の Lv1 が元の技の最大より弱くない）に何度も落ちた。威力でなく再使用・数・範囲で直す。`npm run balance-moves` は2回回すと落ち着く。
- **光の入れ物（加算）に茶色や濃い色を入れると白っぽくなる**（すなあらしが雪に見えた）。ふつうの色の粒は `blend: normal` で入れ物の外に描く。
- **範囲の塗りが絵を隠す**（つのでつくが白い四角に見えた）。絵で見せる技は `hideShape`。前に出す絵は、根元が使ったポケモンの体に隠れないよう、絵の中で前へずらす。
- **作者は「見た目と当たり判定が同じ」を求める**（メガホーン: 扇形でなく槍が届く直線）。絵を決めたら当たり判定の形もそれに合わせる。
- 絵の指摘は形の言葉で来る（クワガタに見える・台形の上底と下底が閉じる・犬歯を長く）。1回で直らないことが多いので、正面・横・斜めを並べた写真で確かめてもらう。
- ゲストでは伝説戦の `spawned` が立たない（出現はホストから届く）。ゲストでも動かす処理は、出ている敵から探す。
- 伝説の扱い（`devGrant.ts` の「伝説以外の実績」など）を種族で決めていると、レッドの手持ち（ピカチュウ・カビゴン）まで伝説になる。ID（`red-`）で外した。
- 実績を足したら、6言語の名前・説明が無いとテストが全部落ちる（読み込みの検証）。
- 圧縮した書式の JSON（`playables.json`・`pickups.json`）を `JSON.stringify` で書き直すと全体の書式が変わる。行を文字列で足す。OneDrive が一瞬ファイルを掴んで書けないことがある（書き直す前に壊れていないか確かめてから、もう一度）。
- このパソコンには Python が無い。スクリプトは Write で `.cjs` に書いて node で実行する（シェルのヒアドキュメントに長いスクリプトを入れると、引用符で止まることがあった）。
- 組み込みのブラウザが隠れていると、ゲームのループが進まない。`window.game.loop.sleep()` してから `loop.step(t)` を回し、そのあとスクリーンショットを撮る。`?level=` を付けると進化の演出でゲームが止まる。ファイルを書き換えると Vite がページを読み直し、途中のスクリプトが切れる。
- 開発サーバーのタイトルの版は、サーバーを起動したときの版のまま（起動し直すと直る）。

### 9.5 難しさの測り方（J6）
- ジョウトは「ジョウトの強化を全部3段階ほど買った状態が丁度よい」。`BALANCE_REGION=johto BALANCE_UPGRADES=3` で、カントーの強化なしと比べて同じくらいの手応えになっているかを見た（07 の86章）。
- 強化の「成長」でレベルが上がると雑魚の HP も上がるので、強化があっても早くクリアするとは限らない。自動プレイヤーは倒れないので、生き残れるかは作者の手触りで決める。
